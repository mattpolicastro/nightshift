## Context

`loop.Ctx.repo` is the harness's bare `repo.git`; `Ctx.ref` names the run branch. `loop.finals` performs final coverage/acceptance and pauses ready. `cli._publish`, under the existing run lock, checks `_remote`, pushes, reconciles/adopts a PR, and pauses for human checks. Neither path refreshes `pr_base`. The run repository's own origin points to the source clone, so fetching that origin would not necessarily fetch the hosted base.

`loop.section_evidence` passes `RunState.section_base[section]` and the current head to `evidence.gather`, which uses a two-tree diff. If a base merge occurs between those commits, its upstream additions become mutation candidates. Changing only publication would leave this defect in resumed/revision sections.

`nightshift/specloop_intake.py::publish_pending` saves human checks before calling publish in a receipt keyed by `(change, head, pr)`. It discards a receipt when status reports another head, and skips `human_checks` runs without a matching receipt. Publishing H as merged M in one invocation would therefore lose recovery after a lost publish response or interrupted comment delivery. The publication path must preserve this existing contract without editing intake. The same caller caps `publish --json` at 30 seconds (`POLL_COMMAND_TIMEOUT` and `_bounded_run`); full verification takes 75–150 seconds. Doing integration and verification in publish would be killed on every poll when the base moves, creating a livelock.

Read sources include README, CLAUDE.md, engine documentation, known limitations, the affected code, and the current interface, run-actions, preparation, revision, intake and parallel-evidence requirements. No AGENTS.md exists in this checkout or its ancestors. #14 is archived here; preserve its strict authored scenario validation and runtime filtering.

## Goals / Non-Goals

Publish a head that incorporates the latest fetched PR base and has passed trusted verification after integration. Keep fetches bounded to one per readiness/publish check; preserve branch history and receipts. Make conflict, failure and interrupted-check behavior testable using temporary local repositories.

Do not change the daemon, supervisor, verification implementation/sandbox, reviewer contracts, manifest, mutation execution, or `finish`. Do not attempt to fix the earlier spec-stage collisions in this change. Do not bypass target validation or change PR adoption/reconciliation. Do not add an automatic rebase, force push, conflict-resolution agent or hosted service dependency to tests.

## Decisions

### Driver owns preparation; publish only checks freshness

Add `loop.prepare_publish(ctx) -> bool`, called only by `loop.finals` in the driver under the run lock. A true result means the current head is eligible for final checks; false means the helper durably paused with diagnostics. Call it before coverage/acceptance and reload `head` afterwards so final checks evaluate the merged tree. If final checks append tasks, the next trip through finals checks again. No readiness notification precedes this gate. The driver has no daemon command timeout; trusted steps retain their own manifest timeouts.

Share a transport helper `loop._fetch_publish_base(ctx, remote, *, timeout) -> str` and a read-only predicate `loop._publish_needs_prepare(ctx, base, head) -> bool`. The predicate checks ancestry and durable verification state, including a pending intent, `retry_verify`, or a recorded integration whose `verified_head` differs from the actual head. It never reconciles an intent, constructs a merge, advances the branch or executes verification. Legacy runs with no integration state use actual ancestry; an already incorporated base alone adds no new verification obligation.

Resolve the source clone's origin with `git -C <m.repo> remote get-url origin`; the run repository's origin points to that clone and is not authoritative. Fetch exactly `refs/heads/<m.pr_base>` into dedicated `refs/specloop/publish-base` in the run repo with `--no-tags` and an explicit forced destination refspec. Resolve relative local origins against the source clone. Do not mutate source refs, configuration or working trees. Use argv, noninteractive prompting and the user's credential-helper configuration as `_push` does. The driver passes a 300-second fetch timeout; publish passes **20 seconds**, with no internal fetch retry. The helper returns a SHA only after this fetch succeeds; a timeout, error or missing branch must never reuse an old destination ref. Keep merge operations on `seal.git`'s safe flags and `seal.IDENTITY`; credentials are needed only for transport.

In the driver, a failed fetch or missing base pauses unscheduled as `base_fetch` with the requested ref, diagnostic and explicit `specloop resume <change>` instructions, leaving the branch and any verification obligation unchanged. Build-only manifests need no GitHub target to run this driver gate.

### Bounded publish hands unfinished work back to the driver

In `cli._publish`, preserve the ready-state precondition, existing run lock and `_remote(ctx)` target validation. After validation, fetch once with the 20-second timeout and check `_publish_needs_prepare`. Publish **never** calls `prepare_publish`, a merge helper, intent recovery, `verify.run_steps`, `finals`, or the driver inline, even for a previously interrupted integration. It does not move the run head. There is no entry-head comparison or post-merge deferral path in publish.

If the fetched base is incorporated and no verification obligation remains, continue the existing push, adopted-PR reuse/reconciliation, `published` event and `human_checks` pause at the same head. Push/PR transport failures retain today's retryable readiness and reconciliation behavior.

If integration or verification is needed, atomically save `st.status = "running"` and `st.pause = None`, preserving tasks, gates, PR, integration intent and receipts. Record the scheduling reason and fetched base/head for diagnosis without treating the fetched base as integrated. Do not clear an independently requested stop. Return before push, PR lookup/creation, publication events or `human_checks`; do not mark any verification obligation satisfied. The unchanged supervisor schedules the running run, re-enters `finals` once existing task/gate work is complete, and lets `prepare_publish` fetch again, integrate and verify. Successful final checks regenerate the complete human-check list and trailing publish instruction at the actual merged head and pause `ready_to_publish` again. A manual operator without `serve` can run `specloop run <change>`, then retry publish after readiness.

For direct `publish --json`, the handoff returns exit 1 and exactly `{"version": 1, "error": "<retry explanation>"}`, without `outcome` or `reasons`. Set `args.document` directly as `_locked_command` does for a busy lock. Explain that preparation was scheduled, nothing was published, and publication can retry after the driver restores readiness. Plain publish prints that explanation and exits 1 without a traceback. For `act publish` (internal arguments have a document but no JSON flag), return the same explanation through `reasons` and exit 1, retaining its version-1 `refused`/`detail` format. Direct daemon publication receives the retryable error, never a domain refusal that would be cached and labelled `needs-human`.

A publish fetch timeout, transport error or missing base returns that same retryable top-level error with the requested ref and a retry explanation. Leave `ready_to_publish`, its checks, PR, head and verification state unchanged; there is no successful freshness result on which to act. Do not enter `base_fetch` from publish. A subsequent poll retries the fetch. Existing wrong-target and not-ready refusals remain domain refusals; publish does not diagnose a merge conflict or drift by executing work itself. Conflict/drift pauses arise only in the driver and retain their diagnostics through status and explicit recovery.

### Receipt recovery across driver preparation

Intake first saves an H-keyed receipt, then publish may hand back to the driver while leaving H unchanged. If the handoff response is lost after the atomic save, status reports `running` and the supervisor still schedules it; intake does not publish a running run or mark its old receipt delivered. If interruption precedes that save, the run remains ready and a later publish repeats the handoff. Neither path advances the branch in the CLI.

The driver may advance H to M and crash before verification success is saved. State stays running with the durable obligation; the supervisor restarts the driver, which recovers and checks the head before readiness. Until then, intake cannot publish or create an M-keyed publication receipt. After the driver reaches readiness at M, existing intake discards the H-keyed receipt and saves a fresh M-keyed receipt containing all human checks. A later publish fetches once and pushes M only if no new preparation is required. This naturally gives intake the status/receipt refresh it needs, without a second head-advancement mechanism inside publish.

If the stable publish response is lost after `human_checks`, its receipt already matches M and existing recovery supplies the result. Comment failure before or after remote acceptance reconciles the same round marker exactly once. A later revision gets its own receipt. Status reports the actual Git head; do not alias it to H, rewrite daemon receipts from the CLI, relax head matching or remove the comment requirement. `issue-intake` Publication needs no MODIFIED delta: its publication/comment effects and recovery remain intact after retryable preparation.

### Preserve history and make conflicts transactional

Let H be the current run head and B the successfully fetched commit. If B is an ancestor of H and there is no unresolved verification obligation, there is no integration work: perform no merge and no extra verify. This ancestry check also supports admitted runs without new state fields; an admission SHA need not be invented from a stale local branch. Normal unchanged-base operation costs one network fetch, plus inexpensive local ancestry checks.

Otherwise compute a merge in a disposable harness checkout using `--no-ff --no-commit`, with hooks/signing disabled and harness identity. Do not merge in the source clone. On conflicts, collect sorted unmerged paths using NUL-delimited Git output, retain a diagnostic, discard the disposable checkout, and pause as `base_conflict`. The run ref and tree remain exactly H; no partially merged index is installed in the bare repository. Operational merge errors are diagnostics, not a successful merge or a fabricated file conflict.

On a clean merge, create a commit M whose first parent is H and second parent is B, even when H could fast-forward to B. Import M into the bare repo, then advance `Ctx.ref` with compare-and-swap `update-ref <ref> M H`. Never reset, rebase or force-push the run branch. A ref mismatch prevents publication and reports an unscheduled infrastructure pause. Upstream changes are trusted base content, not agent-authored files to run through the seal path allowlist.

### Durable verification obligation

Add an optional `base_sync` dictionary to `RunState`, defaulting to empty and loaded with `raw.get`, preserving unknown-field compatibility. Its documented keys are `base`, `previous_head`, `merged_head`, `verified_head`, `receipts`, and `retry_verify`. Record the B/H/M integration intent with empty `verified_head` **before** moving the branch. Keep B recorded for evidence attribution after the check succeeds; do not overwrite it merely because a later fetch conflicts. Set `retry_verify` on conflict as well: a human may incorporate the fetched base during repair, and ancestry on resume must not bypass checking that repair. On recovery with the fetched base already incorporated, record that base and verify the repaired head before clearing this flag. Retain each attempt's diagnostics and receipts in a fresh directory under `final/base-sync/`, never overwriting a failed attempt.

Recovery reconciles a saved clean-merge intent against actual ancestry: at H, complete/retry the saved update under the lock; at M or a descendant, retain the verification obligation; an unrelated ref is an infrastructure error. A conflict-only `retry_verify` record has no M to install. A crash after ref advancement or after verification but before saving success therefore cannot treat B's ancestry as proof of verification. Re-fetch first on the next driver preparation; if origin moved again, integrate its latest B before verifying. A publish check with this pending intent only schedules the driver, even if B is already an ancestor of the current head. Preserve the prior obligation until the resulting head passes.

Run `verify.run_steps(ctx.repo, head, m.verify, m, out)` and evaluate with `verify.ok(receipts, m.prepare + m.verify)`. This automatically preserves preparation ordering, expected exits, timeouts, network separation and source immutability. Clean transient source/build trees with `verify.cleanup`, retaining logs and receipts. On success save the exact `verified_head` and receipt directory. A later changed head with recorded integration requires a fresh driver check before publication; a repeated check of the same successful head does not.

On failing prepare or verify receipts, retain M on the run branch, pause as `base_drift` with B, head, failure summary and receipt paths, and perform no external publication. Do not turn this into `_final_fix` or silently append acceptance tasks. Unexpected verification infrastructure errors also block publication, preserve the obligation and available logs, and use unscheduled `infra` with an explicit recovery detail.

Human recovery uses a checkout of the actual run head (including M after drift), commits a descendant repair on the source branch, then uses existing `specloop resume` to import it through `_sync`. Resume alone is not proof of a fix: the persistent obligation forces verification again, including when B is unchanged. Conflict recovery likewise starts from the retained run head. To request agent work without changing `specloop/revise.py`'s pause policy, an operator may explicitly `resume --no-run` and then queue `specloop revise`; existing `agent:revise` applies once the run is running. Direct revision while paused as `base_drift` remains refused. No daemon or revision-rule changes are required or promised.

### Keep section evidence attributable to the section

Add `loop._evidence_base(ctx, section, head)` and use its result as the existing `evidence.gather` base argument. Preserve an absent section base as absent, preserving the existing skip behavior. Without an integrated B, keep the existing section baseline S unchanged. If B is already an ancestor of S, likewise use S.

When a recorded integrated B is an ancestor of the evaluated head but not S, compute a synthetic comparison commit E by merging B into S in a disposable checkout without advancing any run ref. Diff E against head through the existing gather interface. E contains the earlier sections plus upstream content, so this removes the merge's base-only first-parent changes while retaining only changes since this section started. It is the section-scoped equivalent of comparing the run against `git diff B...head`; using that full-run diff alone would incorrectly include earlier sections. Persist the B/S/E/head identifiers with gate diagnostics, and retain the integrated-base record across revision rounds and reloads. A pending merge not yet present in head must not affect its evidence baseline.

If this comparison merge conflicts, pause `gate_evidence` with the paths and baseline identifiers before generating mutants; do not fall back to a contaminated diff, silently skip mutation, mark evidence passed or append strengthening tasks. Existing behavior is unchanged when no base integration crosses the section. Keep known-scenario filtering, mutation-path filtering, sample counts/seeds, classifications, score/timeout rules and reviewer rules untouched. Do not edit `specloop/evidence.py` or `specloop/manifest.py`.

## Risks / Trade-offs

- The remote base may move after the fetch and before push/hosted CI. This checks one current snapshot per attempt; it cannot atomically lock the hosted base and deliberately does not spin until the remote stops moving.
- Base movement at publish adds a driver scheduling cycle and another CLI retry or daemon poll before the push. Full preparation runs outside the daemon's 30-second cap, avoiding a kill-and-retry verification livelock; a continuously moving base can still require multiple genuine preparations. The 20-second fetch bound leaves response overhead below that cap; existing push/PR timeouts are unchanged and may still be handled as ambiguous retries. The daemon uses its existing failure/health accounting without adding `needs-human`. Manual callers need `serve` or an explicit `specloop run`, then a publish retry.
- Persisting integration intent before ref movement makes interrupted work recoverable but adds state transitions. Tests must cover both sides of the ref update and success save.
- A synthetic section baseline may conflict even if the actual run merged cleanly because later work resolved the overlap. Pausing with diagnostics is preferable to attributing upstream code to the section; do not relax evidence rules automatically.
- Fetch authentication may fail on an offline host. No stale-base fallback is allowed. Driver `base_fetch` requires explicit resume; publish fetch failures remain ready and retry on later polls, preserving checks and evidence.
- New pause details are visible through existing status; the daemon/UI's specialized action lists and attention categorization are not extended here. Operators recover through the explicit CLI instructions.
- Human checklist for the implementation PR: on the next few real runs, record fetch and added verification durations, total readiness-to-publication latency, repository size and whether the base moved. Judge whether the extra verify is acceptably fast on large repositories. CI can prove ordering and the unchanged-base fast path, but cannot establish representative live publish latency. This observation is not an implementing-agent task.
