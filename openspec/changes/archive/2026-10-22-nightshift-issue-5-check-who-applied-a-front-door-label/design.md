## Context

`nightshift/specloop_intake.py::_label_events` reads every REST issue-event page, selects the last labeled/unlabeled event for each requested label, validates that it is a current application, then discards everything except its ID. `_approval_event` wraps that helper. `propose_pending`, `admit_pending`, and `revise_pending` use IDs for replay protection but do not authorize actors. `queue.trusted` already limits prompt text to OWNER, MEMBER, and COLLABORATOR; that is a separate check.

Read sources include README.md, CLAUDE.md, the intake implementation and its tests, `tests/conftest.py`, and all requirements in `issue-intake` and `pr-revision`. No AGENTS.md exists in this checkout or its ancestor directories. The prerequisite #12 is represented by the archived file-input change and the current File based drafting input and Durable drafting payload requirements.

Existing specifications are retained except for the explicit authorization qualifiers in the MODIFIED deltas. Engine routing, successful delivery, refusal details, blockers and blocker-independent recovery, publication, pause behavior, feedback selection, and durable payloads retain their existing contracts. A label rejection is distinct from a drafting/admission/revision refusal.

## Goals / Non-Goals

Authorize the actual label actor before a trigger causes work or recovery delivery, select the newest application before evaluating trust, and explain rejection without comment spam. Tests must exercise production trust decisions with injected GitHub, git, CLI, and launcher boundaries.

Do not change worker claims, publication eligibility, running-process cancellation, text trust, or configuration. Use the existing association policy rather than adding the optional allowlist alternative. Do not modify files assigned to the listed concurrent changes.

## Decisions

1. **Preserve event identity and expose actors.** Add `_latest_label_events(repo, number, labels, *, runner) -> dict[str, dict]` in `nightshift/specloop_intake.py`. It owns the existing paginated query and validation, selecting the final labeled/unlabeled event in GitHub's chronological page order. Require a positive integer event ID (excluding booleans). `_label_events` remains an ID-map compatibility wrapper and `_approval_event` retains its integer return interface. Authorization and receipt identity must derive from the same selected event objects, not independent queries. Never filter to trusted actors before selecting the latest event.

2. **Resolve the actor, not another author.** Add `_label_actor_association(repo, event, *, runner) -> str | None`. Read only `event.actor.login` as the principal; reject absent, null, malformed, or deleted actors. Do not infer trust from `actor.type`, `site_admin`, label permissions, or an issue's `author_association`. REST label events are not assumed to carry the comment-style association field. Resolve the actor using read-only GitHub endpoints through the injected runner:
   - Read `GET /repos/{repo}` for the repository owner's login and type. A matching User owner resolves to OWNER.
   - Otherwise check `GET /repos/{repo}/collaborators/{actor}`. HTTP 204 resolves to COLLABORATOR; this is the collaborator-membership endpoint, not a public repository's read-permission result.
   - If that check returns 404 and the repository owner is an Organization, check `GET /orgs/{owner}/members/{actor}`. HTTP 204 resolves to MEMBER; 404 supplies no positive membership evidence.
   - All other actors resolve to untrusted. Normalize the result against `queue.TRUSTED_ASSOCIATIONS`. Encode login path components and accept only well-formed login strings. Add a small local status-response reader using `gh api --include`; preserve normal `queue.GhError` propagation except for a confirmed HTTP 404 on these membership endpoints. Inspect `queue._gh`'s error output rather than catching every failure as a negative membership answer.

   This avoids inventing an actor-association field absent from GitHub's REST event schema. A definitive missing actor or negative membership result produces a rejection comment; malformed responses, missing event identity, 401/403, rate limits, and transport/5xx errors use the existing retry/error path and never authorize work. Do not cache positive membership across polls. A local cache within a poll may avoid duplicate reads for the same repository and actor. Permission changes are evaluated when polling, not reconstructed historically.

3. **Gate all three entry points.** Add a shared `_authorize_label_events` helper consuming selected events and returning whether the requested labels are authorized. For drafting, authorize every currently present configured intake label (`labels.spec_draft`, `labels.ready`); with both present, both latest applications must be trusted. This conservative rule prevents a second alias from disguising an unauthorized trigger. For approval, gate before `_approval_covers_head` so an unauthorized event cannot overwrite the remembered approved head. For revision, gate before feedback/status reads and empty-feedback handling. Return `None` for an ignored item and continue `_each` to later items; rejection is not a job success or a `needs-human` escalation.

4. **Respect lifecycle ordering.** Existing eligibility/pause checks run first. For an issue needing a new drafting round, preserve the dependency gate ahead of rejection comments: an open or unreadable blocker still leaves comments, labels, and receipts untouched. Use the selected events to recognize rearming without writing a new receipt before blockers and authorization pass. Recovery of an existing open PR or receipt bypasses blocker lookup as today but must pass actor authorization before delivery. An unauthorized current event leaves existing workflow receipts, approval-head records, and job identities unchanged; it does not cancel already launched work. Rechecking authorization after restart must not launch duplicate work. Legacy receipts with only integer event IDs remain readable and do not grant trust by themselves.

5. **One explanatory comment per application.** Add `_comment_label_rejection` in the intake module, using the normal self-comment prefix and a stable marker `<!-- nightshift:draft:label-authorization-{number}:{event_id} -->` in that repository's issue/PR thread. State the label, actor login (or unavailable identity), permitted associations, and recovery: a trusted actor removes and reapplies the label; with two intake labels, remove the unauthorized alias or reapply it as trusted. Do not remove the label, add `needs-human`, or change other labels. Read all comment pages; if the marker already exists, do not POST or PATCH it. Different label applications have distinct markers. Use the existing `draft` marker namespace because `queue._gh` only reconciles `draft`, `admit`, and `publish` markers; no `queue.py` change is needed. A lost successful POST response or a daemon restart must find the existing comment before another POST. Internal `queue._gh` reconciliation may PATCH the same body to that comment; ordinary repeated polls must not PATCH it. Failure to read comments must not be treated as an empty thread. No new rejection receipt is needed. The guarantee assumes the existing single-daemon deployment and comments that have not been externally deleted.

6. **Tests and compatibility.** Add new tests in `tests/test_specloop_label_authorization.py` and, if useful for size, `tests/test_specloop_label_authorization_recovery.py`. Mark them `pytest.mark.real_trust`, because `tests/conftest.py` otherwise grants trust to association-free legacy fakes. Parameterize the required two test names across draft, ready alias, admission, spec revision, and build revision. Exercise actual membership response parsing and the trust gate, not a monkeypatched boolean authorization result. Supply explicit trusted actors and membership responses in shared `DraftGh`/`ApprovalGh` fixtures in `tests/test_engine_routing.py` and `tests/test_specloop_approval.py`; inherited revision fixtures then keep their existing purpose. Update any other unreserved fixture producers that require the new read-only queries. Never weaken production missing-identity handling to keep old fixtures green. Do not edit `tests/test_specloop_background.py` (#8), or `tests/test_specloop_status_json.py`, `tests/test_specloop_act.py`, `tests/test_specloop_state_reads.py`, and `plugins/nightshift/tests/factory.test.ts` (#10).

7. **Validation and integration.** Implement after #12 and retain `--idea-file`, distinct payload lifetime, and original receipt ID shapes. Run focused intake/approval/revision/routing tests as each integration lands, then `uv run pytest` for the definition of done. Associate all new scenarios with `pytest.mark.scenario` IDs. No live GitHub or host application is required for automated tests.

## Risks / Trade-offs

- Membership lookups add API calls and require visibility into the relevant membership. A hidden org membership or insufficient token visibility must not silently grant access. A 404 provides no positive evidence and can conservatively reject a real member. Tokens that cannot read these endpoints may block intake; do not broaden token permissions automatically.
- The association policy trusts all repository collaborators, including collaborators with limited roles, and all provable organization members. It is intentionally the existing OWNER/MEMBER/COLLABORATOR policy rather than a write-permission or administrator-only policy.
- Current membership is not an immutable historical association. Losing membership prevents a later poll from acting; gaining membership can make a still-present event eligible on a later poll. Reapplying the label is the documented recovery path, but trust decisions are not permanently cached as denials.
- GitHub can change labels between the final read and an external operation. This change prevents decisions based on stale applications in the fetched history; it does not make polling and dispatch an atomic GitHub transaction.
- An unauthorized reapplication can hold delivery of previously launched work. Preserve the job and receipt, and resume normal recovery when the current trigger is authorized. Stopping that process belongs to the separate kill-switch change.
- Preserving blocked-issue silence means an unauthorized label on a blocked new draft is explained only when its blockers clear. Existing dependency-gate requirements take precedence during that wait.

Human checks for the implementation PR (not implementing-agent tasks):

- On both a personal repository and an organization repository, inspect real label-event responses after trusted application, removal, and reapplication. Confirm the event actor is the person who applied the label, IDs are stable, and pagination preserves ordering.
- With the deployed token, confirm owner, collaborator, and org member resolution using the chosen membership endpoints, including private membership, an outside actor with a limited role, and an inaccessible membership lookup. Verify the intended trust boundary rather than assuming comment-author association exists on label events.
- In a disposable repository where the role setup permits it, confirm one rejection comment across polls/restart and successful recovery after a trusted reapplication. If GitHub prevents a non-collaborator from labeling, record that limitation; injected events still prove the defensive behavior in CI.
