## Context

`nightshift/specloop_intake.py::revise_pending` reads the remote head's committer date and passes it as `since` to `queue.pr_feedback`. That helper returns rendered strings, losing the GitHub identities. Intake keeps only the latest round in `state_dir/revisions/<owner>__<repo>/<pr>.json`, and a new label event can replace it. Both spec-stage `propose` and build-stage `revise` therefore need the same consumption history.

Read sources: README.md, CLAUDE.md, the queue/intake/job implementations, revision and authorization tests, and the full requirements of `pr-revision`, `issue-intake`, `specloop-interface`, `paused-job-delivery`, and `background-job-control`. No AGENTS.md was found in this checkout or its ancestors. #5's authorization implementation is present. Existing specs are preserved except for the explicit MODIFIED `pr-revision` deltas: branch-tip filtering causes the reported bugs and must change.

## Goals / Non-Goals

After the one-time legacy baseline is established, every eligible unconsumed ID can contribute to one successful revision, regardless of comment time, commit time, body equality, or label-event identity. A round uses a fixed snapshot; later comments remain pending. Failures and delivery retries must neither lose that snapshot nor reset successful consumption.

Keep existing author trust, self-comment exclusion, inline locations, JSON feedback blocks, UTF-8 `--idea-file` input, branch/head checks, PR ownership checks, pause, cancellation, and human merge boundaries. Do not change the worker engine or promise exactly-once CLI execution when its commit has no durable result. Do not require GitHub, an agent provider, or a host UI for automated verification.

## Decisions

1. **Expose structured feedback without changing worker callers.** Add `queue.pr_feedback_items(repo: str, number: int, *, runner=_gh) -> list[FeedbackItem]` in `nightshift/queue.py`, with a small immutable record containing `id: str` and `block: str`. Keep `pr_feedback(repo, branch, since=None, ..., strict=False, number=None) -> list[str]` and its worker-facing timestamp semantics intact; specloop switches to the structured helper without a `since` argument. Reuse formatting helpers where useful, without broad refactoring.

   Read all pages via `gh api ... --paginate --slurp` from `repos/{repo}/issues/{number}/comments`, `repos/{repo}/pulls/{number}/reviews`, and `repos/{repo}/pulls/{number}/comments`. REST gives a positive integer `id` for every source. Qualify it as `conversation:<id>`, `review:<id>`, or `inline:<id>`; reject booleans and malformed/missing IDs on otherwise eligible records. Repository and PR scope comes from the receipt path, not the change slug. Do not mix REST numeric IDs with GraphQL node IDs or use body hashes or timestamps as identity.

   Apply `queue.trusted(item, "author_association")`, `_block`, and `has_instructions` before returning actionable records. Preserve review-state suffixes, Unicode/blank lines, inline `path` and `line` with `original_line` fallback. Keep the current category order (conversation, review, inline) and API order within each category. Identical repeated IDs with identical blocks collapse to one; conflicting duplicate records cause a retryable read error. Equal bodies with different IDs remain separate instructions. All endpoint/page/shape failures propagate; never deliver a partial snapshot or treat failure as empty feedback. Factor the paginated raw-record read into a private helper so legacy initialization can enumerate every trusted ID, including currently blank or self-prefixed bodies, without broadening the actionable snapshot filter. For migration, conversation/inline records use REST `created_at`; review bodies use `submitted_at`, the review endpoint’s creation/submission equivalent. Do not use edit times. Missing/invalid required migration timestamps fail the migration; ordinary ID-based selection does not require timestamps.

2. **Keep the ledger in the existing per-PR receipt.** Extend new receipts with `feedback_state_version: 1`, `consumed_feedback_ids: list[str]`, and `feedback_ids: list[str]`. Existing `feedback: list[str]` remains the command payload, positionally aligned with `feedback_ids`. Store consumed IDs uniquely in sorted order; preserve unknown receipt fields when updating. Keep cumulative IDs when creating a replacement round, when a round is empty or refused, and when its `change`, `head`, event, or stage changes for the same PR. Do not prune IDs when comments disappear. Validate known field types and version; corrupt or unsupported state raises through the existing item error path, never resets to an empty ledger.

   A PR with no revision receipt starts with an empty consumed set, so every eligible historical ID is available, including comments at or before the tip. This is intentional: commit time is no evidence that a comment was addressed. No GitHub commit-date lookup is needed for new or already migrated receipts; the one-time legacy fallback in decision 5 is the only exception. A same-ID body edit before selection contributes its current body; an edit after selection cannot change that round's saved payload. After consumption, the ID remains excluded even if its body or timestamps change.

3. **Persist selection before dispatch.** After normal eligibility and #5 authorization, collect/recover an existing attempt before considering a new one. For a new attempt, read the complete feedback set and subtract consumed IDs. Save the selected IDs, rendered blocks, existing event/round ID, and cumulative set with `_save` before `_start`. Both synchronous injected runners and production jobs must see this ordering. Use the current JSON file for `revise` and distinct idea files for `propose`; pass only rendered blocks across the unchanged CLI boundary. Running or stopped jobs retain their original snapshots. Never mark every comment visible at completion consumed.

4. **Acknowledge successful work before notifications.** For an admitted change, union exactly `feedback_ids` into the cumulative set when a validated `outcome: revised` with a landed commit is durably saved. Do this before posting the completion comment or removing the label, without waiting for build completion or publication. For a spec revision, first durably save its validated `drafted` result, then use existing head checks and push delivery; union its IDs after the push succeeds, before notification/label effects. If the push response is lost, the saved result and existing remote-head reconciliation permit retry without drafting again. Receipt save failure prevents subsequent notification or replacement of the round. Repeating the union is harmless.

   An empty, refused, rejected, needs-input, invalid, failed, or stopped attempt consumes nothing. Existing needs-human handling remains; after resolution a new attempt may select the still-unconsumed IDs and current bodies. Preserve earlier successful IDs through those outcomes. A successful durable result awaiting notifications takes precedence over a newer authorized label event: finish its accounting and delivery before selecting another round. Use its original marker, and do not remove a newer label application while delivering the older event; re-read the latest application immediately before label removal. The newer request can select remaining IDs on a later poll. Current authorization is still required before collecting or delivering, and denial leaves state untouched.

   Extend `queue._reconcile_intake_comment`'s anchored marker pattern from `draft|admit|publish` to `draft|admit|publish|revise`. Keep both legacy markers and round-qualified markers valid. `_comment`'s preflight lookup alone cannot protect the internal `_gh` retry after a lost POST response. On that retry, search all comment pages for the exact original marker and PATCH the existing ID; only confirmed absence permits another POST. Lookup failure propagates without a blind POST, and existing pause guards apply to every retry. Test with real `_gh` and reconciliation code, mocking only `queue.subprocess.run` and sleep: the first POST stores remotely but returns a transient error, reconciliation finds the marker on a later page, and exactly one comment-create call occurs. Also cover failed reconciliation reads and a distinct round marker; retain draft/admit/publish behavior.

5. **Automatically migrate legacy receipts once.** An existing revision receipt without consumed-ID metadata is legacy; a version-1 receipt missing required fields is corrupt, not legacy. After authorization and before collection can overwrite the old receipt, initialize its baseline from the complete trusted raw feedback history. Use a recorded top-level `saved_at` timestamp, accepting `updated_at` as a legacy alias when `saved_at` is absent. Compare timezone-aware instants inclusively: every trusted ID with `created_at <= cutoff` is consumed, regardless of current body or prior outcome. Reviews use `submitted_at` as specified above. Later IDs remain eligible even when older than today's tip. This is an explicit compatibility approximation, not a claim that the historical payload contained every such comment.

   This checkout's `specloop_job.save` records no save timestamp, so receipts from it use the fallback: fetch the **current PR head** committer date once and consume trusted IDs at or before it, matching the old strictly-newer-than-tip rule (reviews use submission time). Do not use file mtime, job start/finish time, current wall time, or the receipt's old head as substitutes. A present malformed saved timestamp is an error; absence of both supported timestamp fields enables fallback. A failed feedback/commit read or atomic save leaves the old receipt unchanged, dispatches nothing, and retries normally. No initialization prompt or operator editing is required.

   Atomically save version 1, sorted `consumed_feedback_ids`, and `feedback_migration: {source: "receipt_saved_at" | "branch_tip", cutoff: <UTC instant>}` before any new dispatch or delivery. On restart never recompute an initialized baseline, even if the tip advances. Preserve unknown fields and all original job/result/payload/event/marker fields. Legacy snapshots lack exact IDs: retain their original `feedback` and mark `legacy_snapshot: true`, omitting `feedback_ids` only for that retained snapshot; do not infer positional IDs by matching text or consume additional IDs on its completion. New snapshots must have aligned IDs and remove `legacy_snapshot`. Saved work finishes under existing authorization, pause and stop rules before a newer event selects feedback. A stopped legacy job stays held; migration never clears stop intent or launches a replacement. This baseline is the sole exception to success-based consumption for new rounds. A PR with no receipt still starts with an empty consumed set.

6. **Limit overlap with work in flight.** The required production edits are `nightshift/queue.py` (structured reads and `_gh` marker reconciliation) and the revision path/local helpers in `nightshift/specloop_intake.py`. `README.md` around line 114 is also in scope to replace branch-tip guidance with consumed-ID behavior, including automatic legacy migration and the need for a new comment after consumption. The intake overlap with #46 is unavoidable: selection and acknowledgement live there. Confine edits to `revise_pending` and new revision-only helpers; do not modify `publish_pending`, admission/proposal paths, or shared `_start`/`_collect` behavior for other stages. Reuse `_save` and existing job APIs without modifying `nightshift/specloop_job.py` or `nightshift/specloop_client.py`.

   Also avoid `nightshift/touchpoints.py`, `specloop/critic.py`, `specloop/evidence.py`, `specloop/loop.py`, `specloop/manifest.py`, `specloop/propose.py`, and `specloop/state.py`. Put new tests in `tests/test_pr_feedback_ids.py`, `tests/test_revision_feedback_state.py`, `tests/test_revision_feedback_consumption.py`, `tests/test_revision_feedback_recovery.py`, and `tests/test_revision_comment_retry.py`. Do not edit the concurrent work's test files: `tests/test_mutation_measurement.py`, `tests/test_mutation_prose_annotations.py`, `tests/test_mutation_skip.py`, `tests/test_mutation_source_filtering.py`, `tests/test_specloop_base_evidence.py`, `tests/test_specloop_base_publication.py`, `tests/test_specloop_base_sync.py`, `tests/test_specloop_base_sync_recovery.py`, `tests/test_specloop_evidence.py`, `tests/test_specloop_in_flight_paths.py`, `tests/test_specloop_propose.py`, or `tests/test_touchpoints.py`.

7. **Migrate existing regression expectations deliberately.** Supply stable IDs and REST response shapes in `tests/test_specloop_spec_revision.py`'s shared `RevisionGh` and relevant unreserved fixture producers. Update timestamp-based specloop assertions in `tests/test_specloop_spec_revision.py`, `tests/test_specloop_build_revision.py`, and `tests/test_specloop_label_authorization.py` to use explicitly consumed IDs where they mean old feedback. Explicitly migrate the recovery fixture/assertions at `tests/test_specloop_label_authorization_recovery.py:802-810`: after trusted reapplication, deliver the original saved result with its event and marker, make zero new revision dispatches, retain the newer label application, and handle that request on a later poll using the consumed set. Explicitly migrate the timestamp wording at `tests/test_specloop_build_revision.py:92` to unconsumed-feedback wording, seeding consumed IDs for fixtures that formerly meant “already addressed” solely by timestamp. These changes are required because the old assertions demand the duplicate dispatch and timestamp cutoff this change removes; explain that rationale in the implementation PR. A second event alone must no longer append another round. Keep worker timestamp tests in `tests/test_revise.py` unchanged. New authorization tests use `pytest.mark.real_trust` and explicit associations; never relax production validation to accommodate association-free or ID-free fakes. ## Risks / Trade-offs

- Full paginated history costs more API calls and the ID list grows with the PR. This is bounded by PR activity and avoids lossy time windows; pruning or shared caching is out of scope.
- Editing a consumed comment cannot request another round. Reviewers must post a new comment. An edit made after selection but before consumption also does not amend the saved instruction.
- Legacy receipts have discarded identities and earlier rounds. Automatic timestamp initialization deliberately treats every trusted comment at or before the saved time as consumed, even if it was never addressed; the no-time fallback inherits the old branch-tip rule once. CI verifies inclusive cutoffs, restart durability, and later-comment eligibility. Deleted historical IDs cannot be recovered, and edited consumed IDs remain consumed. No manual migration step is required.
- Existing single-daemon receipt ownership remains assumed. Local atomic replacement does not provide a distributed transaction with GitHub or recover a CLI commit that never produced a durable result. That pre-existing crash gap remains separate work.
- #46 also edits intake. Integrate its landed revision before implementation and preserve its publication/base behavior; this change never needs to edit the listed engine files.

Human checks for the implementation PR (not implementing-agent tasks):

- On a disposable GitHub PR, record the real IDs for conversation, submitted review, and inline feedback. Consume them, edit their bodies, and reapply the revision label. Verify GitHub keeps the IDs and no new round is queued; a newly posted comment must queue normally. Repeat with an edit during a running revision and confirm the saved snapshot remains unchanged.
- Post another comment during a long revision, complete it, then request another round after the tip advances. Confirm the new comment is included once. Verify the before-publication relabel case on an admitted PR.
- Record any live checks not performed as pending. Offline fakes cannot establish GitHub's actual comment-edit identity semantics; legacy migration itself is covered offline and requires no operator checklist step.
