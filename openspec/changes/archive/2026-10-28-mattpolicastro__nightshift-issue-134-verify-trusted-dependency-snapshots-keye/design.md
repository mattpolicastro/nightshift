## Context

`Manifest` currently holds immutable `Step` tuples for preparation and verification. `verify.run_steps()` extracts a sealed commit; `run_extracted()` creates a fresh build, runs network-enabled preparation, then offline checks. Receipt counts include preparation. `evidence.mutate()` baselines each selected step sequence, then runs private mutant builds; narrowed survivors receive another fresh build for confirmation. `loop.prepare_publish()` fetches the configured base and verifies integration under the run lock. The admission implementation is in `specloop/cli.py`, outside this change's runtime scope.

#133 is a prerequisite. The repository already contains its native mutation operators, Dart example and invalid-step classification. Those contracts, the existing verify-preparation requirements, publish-base-sync requirements, and all parallel-evidence-mutants requirements remain in force.

## Goals / Non-Goals

Reuse trusted dependencies when candidate lockfiles match, while preserving fresh candidate source, writable isolated builds, offline verification, receipt semantics and useful fallback. Keep configuration optional and keep tests independent of Dart or external package services.

Do not cache candidate source, generated project configuration or test results. Do not warm during candidate verification, mutation or publish; do not disable existing preparation. Do not provide global caches, configurable eviction, automatic cache repair from candidates, a general artifact service or portable full-copy substitution for APFS cloning.

## Decisions

### Manifest and key

In `specloop/manifest.py`, add frozen `Snapshot(id: str, lockfiles: tuple[str, ...], warm: tuple[str, ...])` and `Manifest.snapshots: tuple[Snapshot, ...] = ()`. Parse `[[snapshot]]` without changing existing defaults or template round trips. IDs match `[A-Za-z0-9][A-Za-z0-9_-]*` and are unique within snapshots. Require nonempty lockfile and argv arrays of nonempty strings; reject NUL in argv. Lockfile paths are canonical repository-relative POSIX paths: no absolute/drive paths, backslashes, empty components, `.`/`..`, glob characters or duplicates. Report malformed settings as `ValueError` naming the snapshot and field.

Reserve variable names beginning `snapshot:` for the harness. Snapshot placeholders in prepare, verify, acceptance and mutation commands must name declared IDs. A warm argv may reference its own snapshot placeholder, ordinary manifest variables, `{src}`, `{build}` and `{sha}`, but no other snapshot or `{mutant_path}`. No new shell interpretation: expansion substitutes argv strings using the existing `expand()` behavior; manifests explicitly invoke a shell when needed.

Add `snapshot_key(src, definition)` in `verify.py`. SHA-256 input is a fixed version prefix followed by sorted lockfile paths and their exact bytes, each path and content encoded with an unsigned 64-bit big-endian length prefix. Sorting makes declaration order immaterial; framing prevents concatenation collisions. Use raw bytes, not text normalization, mtimes, candidate SHA or dependency directory contents. Reject symlinks in every lockfile path component, non-regular files and missing/unreadable files as an unavailable key. Hash the exact read-only extraction being checked, including a mutant's actual tree rather than only its unchanged `sha` argument. Changing unrelated source does not invalidate the key. Store entries by `(snapshot ID, key)` within this run; the copied trusted manifest fixes the warm recipe for the run's lifetime.

### Trusted warming and publication

Add `warm_snapshots(repo, base_sha, manifest, context)` in `verify.py`; it has no candidate fallback and no call site in `run_steps()` or `run_extracted()`. `loop.py` invokes it only with the SHA returned by `_fetch_publish_base()`, never `ctx.head()`, an integrated merge SHA, a sealed candidate or an evidence comparison baseline.

For manifests with snapshots, perform an initial snapshot base sync once per eligible `loop.run()` invocation after checking a requested pause and before dispatching tasks or evidence. Fetch with the existing helper and 300-second driver timeout; this snapshot-only sync neither merges nor discharges publication obligations. Later `prepare_publish()` calls warm from its freshly fetched base before its incorporated/no-pending early return or integration checks. Reuse complete matching entries without executing warm again. No snapshot configuration means no additional fetch or filesystem/event changes. `publish` retains its existing fetch-only handoff and never warms inline.

Initial snapshot-only fetch failure records `snapshot_sync_failed` and continues existing task behavior using any matching retained entries or fallback. The existing final base-sync fetch failure still pauses as `base_fetch`. A warm failure never changes existing verification or publication verdicts: subsequent prepare/check receipts decide them. Retry warming only on a later base sync, not on a cache miss in candidate execution.

Use a private staging directory beneath `<run>/snapshots/.staging-<unique>/`, with a fresh read-only extraction of the pinned base and a writable `build` containing `home`, `tmp` and `payload`. During warm, `{src}` and `{sha}` refer to that base, `{build}` to this staging build, and `{snapshot:<id>}` to `build/payload`. Run the configured argv once with expected exit `0` and a fixed 600-second timeout. Reuse the existing subprocess/receipt execution machinery with the prepare profile, clean environment, tool PATH, credential denials, read allowlist, no additional writable exceptions, and process-group termination. Do not run `m.prepare` while warming. Retain warm logs and receipts outside the payload; warm receipts do not join candidate `receipts.json` or mutant timeout baselines.

Only payload is published. Require a directory containing regular files/directories; reject symlinks, special files and multiply linked regular files instead of following external targets. After warm terminates, move the payload into a separate staging `entry/payload`, preserve execute bits and remove all write bits recursively. Write harness metadata containing schema version `1`, ID, key, base SHA and monotonically increasing publication sequence into `entry/metadata.json`, then atomically rename only `entry` into `<run>/snapshots/entries/<sequence>-<id>-<key>/`. The final entry and metadata are also read-only. Source, temporary HOME and other build artifacts remain disposable staging; retain logs and receipts separately under `<run>/snapshots/warms/<attempt>/`. Metadata is written by the harness, not accepted from warm output. An interrupted or failed warm produces no selectable entry. Retained logs identify failure; disposable staging is removed at the next locked sync. A crash after publication reuses the complete entry on restart.

### Clone consumption and fallback

In `verify.py`, add a small `SnapshotContext` carrying the run's snapshot root and an event callback. Extend `run_steps()` and `run_extracted()` with optional keyword-only `snapshots=None`; old callers remain valid. The context is supplied explicitly, never inferred by walking output-directory parents or exposed through editable manifest vars. `loop.py` supplies it for task, coverage, acceptance and integrated-head verification. Direct verification calls without context use fallback if snapshots are configured.

Before ordinary preparation, create `<build>/snapshots/<id>` for each declaration. On a matching complete entry, recursively create directories and use the macOS libc `clonefile` API for every regular file, with checked return codes and no hard links or byte-copy substitute. Make only the destination owner-writable, preserving execute bits. The context's published `entries` subtree receives a final explicit write denial in both prepare and verify profiles, overriding any broad `sandbox.writable` entry. Denying published entries also protects them during warm without denying the separate staging build's required writes. Existing credential denials remain unconditional. Candidate commands cannot change, chmod, replace or delete the stored entry.

Every step in one prepared command sequence sees the same private `{snapshot:<id>}` path inside its build, just as it already shares HOME and generated build files. A new verification execution, mutation baseline, mutant or confirmation always receives a fresh clone. This is the unit of isolation: do not reset the clone between a prepare step and its dependent check. Nothing from a prior build or mutant is published back to the store.

On an absent entry, a different key, an unavailable lockfile key, invalid/incomplete metadata or payload, missing context, or any clone error (including unsupported filesystem, platform or cross-device cloning), remove the partial destination and supply an empty writable directory at the same placeholder path. Never substitute a stale payload or fall back to `copytree` for a snapshot hit. If partial-destination cleanup cannot establish an empty directory, propagate an infrastructure error before executing commands. Normal missing/stale cases continue the exact configured prepare and check sequence with its existing expected exits, ordering and timeouts. Snapshot failure alone does not fabricate a failed test receipt or a mutation kill.

Preparation remains unconditional. An operator opting in must adapt its trusted recipe to use the snapshot path and retain a real fetch/copy fallback on an empty cache. Existing manifests without snapshots continue unchanged. For Dart, use a dependency-only `PUB_CACHE` payload; copy the current candidate into `{build}/project` and regenerate project configuration there. Do not reuse the trusted base's project tree or absolute-path `.dart_tool` files. The guide demonstrates cache-hit/offline dependency setup and a miss/network fallback while keeping candidate preparation separate from `warm`.

### Events and evidence interfaces

Write `snapshot-events.jsonl` beside each execution's receipts, with one `snapshot_fallback` record per unavailable declaration per build: `id`, requested `key` (null if unavailable), candidate `sha`, reason and execution output path. Stable reasons are `missing`, `stale`, `key_unavailable`, `invalid`, `context_unavailable` and `clone_failed`. Use `stale` only when that ID has retained entries but none matching the computed key; do not leak lockfile bytes or environment values. Forward these events to `Run.event()` through a thread-serialized context callback. Warming emits `snapshot_warmed`, `snapshot_reused` or `snapshot_warm_failed`, with ID/key/base and diagnostic paths. Normal receipts and `evidence.json`/`mutation-runs.json` retain their schemas and meanings.

Thread the optional context through `evidence.gather()`, `mutate()` and `_mutate_one()`. Baselines, narrowed phases and full confirmations call the same consumer and hash their actual extraction. Selection, baseline-before-workers, worker-slot accounting, invalid-step precedence from #133, scoring, exact baseline-derived timeouts and cleanup order remain unchanged. Snapshot clones are setup outside command receipt timers; warm and clone timings do not replace step durations. Existing build cleanup removes clones while leaving the store and diagnostics intact. Store writers and retention run under the existing run lock and outside active worker pools; readers within a pool only consume immutable entries.

### Retention and recovery

Interpret “last 3 snapshots per run” as three completed `(id, key)` payload entries total, not three per ID or three bundles of all IDs. Sort by harness publication sequence; successful reuse does not refresh sequence or create another entry. After each successful publication and at the next locked sync following interruption, retain only the newest three completed entries. A failed warm does not evict a valid entry. More than three declared IDs can therefore cause ordinary misses, which the guide explicitly describes.

No TTL, disk-pressure cleanup, cross-run removal or eviction of diagnostics is added. Validate owned entry names/metadata before pruning and never traverse symlinks. Retry interrupted pruning at the next sync; an I/O failure records `snapshot_retention_failed` rather than claiming the bound was enforced. Temporary staging cleanup and existing per-build cleanup are not eviction of completed snapshots. Legacy runs need no state migration: a missing snapshots directory is an empty store.

### Validation and documentation boundaries

Use temporary Git repositories, tiny dependency files, fake subprocess/clone boundaries and the real manifest parser for portable tests. Add the four named tests: `test_snapshot_warms_only_on_base_commit`, `test_snapshot_key_changes_with_lockfile`, `test_snapshot_clone_is_writable_and_isolated`, and `test_missing_snapshot_falls_back`. Test real `clonefile` isolation on APFS and real source/store/credential denials on unsandboxed macOS; report skips explicitly on unsupported filesystems or nested sandboxes. Doubles do not prove actual COW behavior or sandbox enforcement. No Dart install, hosted service or model call is required.

The guide gets one `## Trusted dependency snapshots` passage and a small TOML example delimited by exact standalone lines `<!-- snapshot-example:start -->` and `<!-- snapshot-example:end -->`. Its structural test accepts exactly one ordered marker pair and parses the intervening text after removing exactly one first line equal to ```toml and one last line equal to ```. Missing/duplicate markers, extra fence lines or invalid TOML block validation. Marker counting is global over physical lines, irrespective of fences, HTML or indentation; no Markdown semantic parser is introduced. Merge the parsed fragment into a minimal trusted-manifest fixture and exercise real expansion plus hit/miss recipe behavior using tiny local stand-ins, without prose-exact assertions.

Preserve all existing assertions. Implementation acceptance is green `uv run pytest` and `uv run python scripts/check_types.py` with no baseline expansion. Relevant tests accompany each code task; the final task runs both complete commands.

## Risks / Trade-offs

- Lockfiles are the declared identity contract. Toolchain changes, environment differences and unlisted dependency inputs are not detected automatically; operators must declare every dependency lockfile and re-admit with an appropriate trusted manifest when those assumptions change.
- APFS clones need compatible source/destination filesystems. Unsupported clone operations preserve correctness through fallback and events, but provide no speedup. Symlink-heavy cache layouts are deliberately unsupported in this first version.
- A fixed 600-second warm can fail for a large project. Failed warming remains an optimization miss; ordinary prepare retains its configured timeout and verdict. Initial snapshot base fetch adds latency only for opted-in runs.
- Three payloads bound entry count, not bytes. Multiple snapshot IDs compete for those slots. A storage failure can leave pruning pending; events must make that visible.
- Restarts can repeat an interrupted warm, but never expose its partial payload. Process-crash tests do not establish physical machine-crash durability.
- Human checklist for the implementation PR: on scheming-vizier, record a comparable run before enabling snapshots and a run after enabling them, including base SHA, lockfile keys, host/toolchain, mutation settings, warm cost, prepare/verify and evidence stage times, cache misses and actual APFS clone execution. Compare repeated verify/mutant stages against the reported approximately 25-second/565-MB dependency preparation cost, with unchanged checks and results. Also inspect the dependency-only payload and guide's Dart recipe for that project. CI cannot establish the real speedup, storage savings or project-specific relocation correctness; leave these checks pending until performed. They are not implementing-agent tasks.
