## Context

Factory currently projects `nightshift status --json` in `plugins/nightshift/server/factory.ts`, dispatches five verbs through `act`, and renders `client/factory.tsx`. Its server shares reads with a 15-second cache; the client refreshes on mount, every 60 seconds while active, on foreground return and manually. Results follow rendered rows, including the Finished disclosure's above-list fallback. Preserve these contracts and all existing accessibility labels and assertions.

`specloop/cli.py` already supplies the branch `head`, real pause `reason`, `action.pause_id` and `pause.since` (the last recognizable pause event's epoch timestamp). `pause_id` is reason plus task, so publication can repeatedly emit `human_checks:` after revision. It is not a unique pause identity. Factory's existing pause projection deliberately exposes only `since` and `auto_resumes_remaining`; do not add internal fields to that projection.

`nightshift/land.py:main` accepts an injectable runner and already performs checklist edits, attestation, finish, bounded CI, validated base updates and `gh pr merge --merge --match-head-commit`. It has no expected-head CLI option. Calling it after a separate preflight alone would let it discover a different initial head. Bind its actual initial reads through the runner, without modifying landing logic or inventing an unsupported flag.

`nightshift/specloop_job.py` persists requests, process identity, inherited lifetime locks, stop intent and results. Its stage traversal, timing validation, receipt paths, wrapper command verifier and escalation verifier are intake-specific. Extend those boundaries by job kind; do not run land through `specloop_client.call` or widen the intake command regex. No applicable `AGENTS.md` was found in this checkout or its ancestor directories.

## Goals / Non-Goals

Make one deliberate confirmation start one recoverable background attempt for exactly the displayed published pause. A lost RPC, revision, restart, long history or failed refresh must not silently authorize another merge or erase a refusal. Preserve existing Factory and intake behavior.

Do not redesign landing, parse PR checklists in the plugin, automatically retry a crashed worker, change the CLI's existing build/daemon forms, or add a terminal substitute for done runs. If landing finishes the run and then refuses, show that refusal and direct the operator to the existing standalone landing recovery; the Factory button still never appears for `done`.

## Decisions

### 1. An isolated operator gateway

Add standalone module `nightshift/factory_land.py` and private worker script `plugins/nightshift/server/factory_land_job.py`. Do not register or forward either through `nightshift/cli.py` or `specloop/cli.py`. The existing `tests/test_land.py:background_references` follows imports inside functions and literal module targets: `specloop.serve` already reaches `nightshift.cli`, which reaches `nightshift.specloop_job`. Registering a gateway there would transitively import land and violate the unchanged `reviewed-pr-landing/Operator entry point` requirement. An operator-only branch or lazy import does not solve that conflict.

Keep dependencies one-way. New `nightshift/factory_land_records.py` contains only record schemas, paths, timing, hold and display decoding shared by the gateway, worker and job control. It imports neither execution entry point nor landing. `nightshift/specloop_job.py` may depend on that control-only module and knows the worker's fixed script pathname for ownership inspection, but cannot import, load, spawn or dispatch it. The gateway alone launches the worker; only the worker imports `nightshift.land` and invokes its existing injectable entry point. This is a separate plugin process entry point, not a hidden module dispatch: no computed module names, reflective imports, shell indirection or dependency-checker exclusions are allowed.

The plugin calls the configured uv executable with `['run', '--no-sync', 'python', '-m', 'nightshift.factory_land', ...args]`, configured checkout cwd and existing Factory PATH. Gateway argv is:

- `uv run --no-sync python -m nightshift.factory_land start CHANGE --pr URL --pause-id ID --head SHA --since SECONDS --request-id UUID --checks-done --json`.
- `uv run --no-sync python -m nightshift.factory_land status [CHANGE] --limit N --json` (default N=20, valid 1–20). Global status returns newest attempts and total; named status also returns an offer and the current attempt for that change, independently of the history limit.
- `uv run --no-sync python -m nightshift.factory_land resolve UUID --json` returns `missing` or the retained immutable payload and bounded outcome without evaluating current eligibility, writing state or launching work. The server compares that payload before replay; malformed UUIDs fail parsing.

Keep `tests/test_land.py` and all its assertions unchanged, including `test_daemon_and_supervisor_never_import_land` and its indirect-reference fixtures. New root `tests/test_factory_land_boundary.py` reuses the unchanged checker and additionally asserts the shared record helper is reachable but the gateway and landing module are not. Inspect shared adapters for imports and launch calls to the plugin worker, not just Python module tokens; exercise jobs list/stop/release and daemon status with subprocess spies that permit process inspection but reject gateway/worker execution. The positive boundary test invokes the standalone gateway's parser and injected launcher to prove the plugin entry remains usable. These checks accompany admission, launch, ownership and handoff changes, so no intermediate task knowingly breaks the existing guard.

Require a canonical GitHub HTTPS PR URL without credentials/query/fragment, a full 40-hex head, safe existing change identifier, a UUID request ID, a finite non-boolean epoch timestamp (including zero and fractional seconds), and `--checks-done` for start. Use canonical serialization without rounding `since`. Unknown fields in persisted version-1 records may be tolerated; conflicting known identity fails closed. Invalid syntax uses the existing singular version-1 JSON error/exit-2 convention. Successful reads and accepted/replayed jobs exit 0; an admission refusal exits 1 with its reason. Runtime exceptions become structured failures, never multiple stdout documents.

The offer is `{change, pr, pause_id, head, since}`. Produce it only from fresh, successful existing-state status with `status=paused`, `pause.reason=human_checks`, consistent `action.pause_id`, a valid PR/head and finite `since`. Missing legacy metadata yields no offer with an explanatory display diagnostic, not an invented value or a failed ordinary Factory list. A named read may still return retained history if the run has disappeared. Reads never launch, signal, collect, acknowledge delivery, repair or compact evidence.

### 2. Admission identity and retry order

Use a canonical repository/PR lock and a durable request index, outside RunState, under the existing Nightshift state root's `landings/`. Check a syntactically valid UUID's existing record before current eligibility or pause-file checks. An identical payload returns the retained refusal, current attempt or terminal result even after finish/merge changes eligibility. Reusing it with another payload refuses without replacing evidence. A retry after an uncertain transport response keeps the original UUID and frozen payload; a new confirmation uses a new UUID.

For a new UUID, under that PR's admission lock, reread current state, compare every offer field, verify remote PR head equals the confirmed published head and refuse a daemon pause, another live/uncertain attempt or an unreleased stopped hold. Different UUIDs cannot concurrently admit the same PR, even under another change name. Admission persists both accepted and domain-refused valid requests; malformed requests do not create state. Pause checked before spawn prevents new work; an already started job may finish while paused, and observations remain readable. A failed eligibility read never becomes approval.

Give a domain-refused valid request its own attempt ID and terminal display summary, but no process or active hold. It participates in bounded history and total counts so admission refusals also survive remount; it cannot displace the current admitted attempt. Known terminal outcomes without cancellation allow a later new confirmation if the run still qualifies. Missing or corrupt evidence never implicitly clears an uncertain hold.

### 3. Durable launch and handoff

Use `<state>/landings/<owner__repo>/<pr>.jobs/<job-id>/` for attempt evidence. Persist `request.json`, a per-attempt `hold.json` naming `job`, a request-index reference and timing before launch; never use or change the intake receipt for that PR. Store the confirmed tuple and request UUID, exact intended land args, start time, a 2400-second reporting budget and deadline. Reporting budget is not a process timeout: existing land retains its 1800-second CI deadline and command bounds. A record is discoverable before acknowledgement, and a new UUID cannot bypass an uncertain launch.

Hold the existing-style lifetime lock from parent preparation across `Popen(start_new_session=True, pass_fds=...)` into the worker. The wrapper argv is exactly `[sys.executable, worker_script, absolute_attempt_directory, str(inherited_fd)]`. Resolve `worker_script` to the fixed `plugins/nightshift/server/factory_land_job.py` under the server-owned `NIGHTSHIFT_CHECKOUT` using existing `host_path` validation and its default `~/Projects/nightshift`. Launch from that checkout through its prepared interpreter environment; use normal absolute package imports, never sys.path edits or dependency installation. The gateway and ownership verifier derive the same path independently from trusted host settings; request and evidence files cannot choose executable or script. Persist interpreter/script identity with process evidence, and refuse a mismatch with the trusted checkout during control. The script path is only identity data in shared job code, never an execution target there.

Persist process-start identity before external work. Keep stdout/stderr in the attempt's log, not in an RPC pipe. The worker and invoked subprocesses retain the FD so wrapper death cannot make executing descendants look idle. A plugin unload kills only its short gateway subprocesses, not the detached job.

Tests inject failure before spawn, after spawn before acknowledgement, and before result persistence. Never relaunch an accepted UUID. An idle attempt with an uncertain missing result remains an explicit recovery-required outcome/hold; inspecting status must not repair it or infer success. A known pre-spawn failure can be recorded as failed without claiming external effects. Preserve evidence; uncertain attempts need operator inspection, not automatic redispatch. Deterministic process-crash tests do not establish power-loss durability.

At worker startup revalidate all five fields against status and the remote head, as well as pause and stop intent, before invoking land. Pass the confirmed tuple to a guarded runner supplied to `land.main([pr, '--checks-done'], runner=...)`. Validate the actual initial PR response and status response delivered to land, and revalidate the confirmed pause/head before pre-finish mutating calls; mismatch raises the existing `land.Refusal` before checks are recorded. Gate the handoff with a tested explicit command classification for the existing argv, refusing unrecognized pre-finish mutations. Do not rewrite remote replies, replay stale reads, or parse Markdown.

After the validated finish transition, the existing land code owns allowed head evolution: finished head or an exactly proven base update may replace the initial head, and its final `--match-head-commit` must name that verified successor. Never force the original SHA after finish changes it, nor adopt an unrelated head in the adapter. Test the actual land entry point with an injected runner, including a push between gateway preflight and land's first read, revision/republication with identical `pause_id`, valid finish/update transitions and final head conditioning. Existing land tests remain unchanged.

### 4. Job control adapters and evidence

Extend `specloop_job.list_jobs` with the landing stage, its timing decoder and per-attempt context; preserve full inventory and existing default/`--all` filtering. Finished landing attempts remain `finished (delivery pending)` and visible by default: there is no daemon delivery or read acknowledgement. Do not use an unrelated intake receipt's delivered flag. Overdue landing is display-only in Factory/jobs/daemon status; there is no `needs-human` escalation, retry or automatic kill.

Add a landing-specific command verifier and escalation adapter alongside `_verify_process` and `_verify_escalation` (currently near lines 978 and 1047). Share PID/start identity/session, group safety, live-member checks, locks and timing primitives. Select the adapter only from validated persisted stage/command context. The landing verifier matches the trusted absolute script path and exact attempt directory/FD suffix, while the intake verifier retains its exact `-m nightshift.specloop_job` contract. Neither verifier imports the worker. Spaces in trusted paths remain literal; altered script/interpreter identity refuses. The intake verifier must continue rejecting the landing wrapper and vice versa. Test real groups for both kinds, including TERM-resistant descendants and wrong-wrapper/path/PID identities.

Stop preserves the existing 5-second TERM and 1-second KILL confirmation bounds, caller/group protections and stop-versus-completion precedence. Worker results cannot erase accepted stop intent. Release uses the landing attempt's `hold.json`: validate exact full job ID, stopped process evidence, idle lifetime lock and consistent regular non-symlink receipt, then atomically remove only its matching `job` reference under control-lock then receipt-release-lock order. Repetition is a no-op; failure preserves the hold; releasing an old attempt cannot affect a successor. Release is offline, launches nothing, and never clears cancellation or deletes evidence. A later landing requires a new confirmation, UUID and current `human_checks` offer; daemon polls do not schedule it. Failed/uncertain jobs are not falsely called stopped or made releaseable.

Landing requests, logs, hold receipts, results, identity and cancellation evidence are retained permanently by this feature. `jobs compact` reports landing as skipped, and automatic intake cleanup never receives landing attempts. This deliberate exception prevents read acknowledgements or item-level delivery metadata from erasing landing evidence.

### 5. Bounded display reads

Retain full logs and result detail on disk. Status selects newest N attempts by persisted admission order (stable job-ID tie-break), default/max 20, returning `total` before slicing. Named status separately returns its current attempt, including unreleased stopped/uncertain holds; deduplicate if it is already in the page. Global status is used for recent outcomes of removed runs; named reads for visible runs and locally tracked changes recover current progress even if the attempt is older than the global page. At most one current attempt exists per PR.

Do not deserialize historical full results/logs to choose the page. Use directory/index metadata, read only selected bounded display summaries, and read the current record by reference. Scanning small metadata to count is allowed; never concatenate unbounded evidence into JSON. Bound each projected detail/progress to 8192 Unicode characters and every identifier/URL field; mark truncation and retain the full diagnostic locally. Limit JSON-escaped UTF-8 output to 1 MiB per CLI response, below the existing 2 MiB subprocess limit; drop oldest history entries with an explicit truncation indicator if needed, never silently drop `current`. Test over 20 records, worst-case escaping and large retained logs, verifying total, order, unchanged evidence and current progress. Older outcomes remain in local evidence; pagination UI is out of scope.

### 6. Plugin RPC and cache boundary

Add separate schemas/descriptors `factoryLandingStatus` and `factoryLand` in `plugins/nightshift/shared/factory.ts`, register handlers in `index.server.ts`, and implement them in a focused server landing module using the existing trusted host-path resolver and a separate literal-argv gateway executor. Keep the ordinary executor's `uv run --no-sync nightshift` contract unchanged; the landing executor uses the standalone module argv in Decision 1, with the same 60-second bound, 2 MiB limit and short-child cleanup. Never extend `factoryVerbSchema` or route landing through `factoryAct`. The landing response is a display projection: identity/offer, attempt/request ID, state, elapsed/deadline, progress, detail/truncation, counts and stale diagnostics. No argv, filesystem paths, credentials, raw stderr or unchecked stdout cross RPC; apply existing home redaction and GitHub URL validation.

`factoryLandingStatus` takes optional safe `change` and bounded `limit`; `factoryLand` takes the exact offer, UUID and literal `checks_done: true`, never executable/cwd/config/timeout. The gateway is authoritative. The server checks shape first, calls the read-only `resolve` command and compares any retained payload before returning its outcome. Only a `missing` UUID proceeds to the last-good displayed-offer check and fresh gateway admission. Apply this order after server restart too; a forged new request cannot use replay to skip admission. A simultaneous first submission that wins after resolve is still deduplicated by start under the PR lock.

Separate caches and in-flight promises for run status and landing status, keyed by query, retain good data independently, use the existing 15-second throttle and generation guards, and bound concurrent named landing reads to four. Landing admission invalidates affected landing/run caches; older reads cannot overwrite newer outcomes. Gateway status/start commands use the short 60-second subprocess limit and 2 MiB buffer; startup returns immediately after durable handoff, never waits through CI. Lost start responses show an explicit unknown result and retain the UUID for retry, not a fabricated refusal by land.

### 7. Confirmation, progress and rendered fixtures

Add Land in its own wrapping control group after the unchanged status action group. It uses existing allowed theme tokens, outlined style and minimum 44-by-44 target; confirmation uses primary Confirm and outlined Cancel. Add button labels `Land <change>` and `Confirm land <change>`, button roles and an alert explaining that the PR's human checks have been completed and landing can merge. Retain every existing label, role, group order, text, disabled condition and interaction. New landing controls are disabled while their submission is pending or the current attempt/hold prevents another start; ordinary action availability remains unchanged.

Freeze the complete offer and new UUID when opening confirmation. Confirm sends only that snapshot; cancel sends nothing. If a refresh changes any field, invalidate that confirmation with a visible stale reason rather than rebuilding it from new props. Server/worker validation still rejects stale requests from another tab. Include the regression where revision republishes with the same `human_checks:` ID but a new head and/or `since` (also test changed time with unchanged head).

Extend existing refresh triggers to read landing status; add no new timer. Landing failures keep prior landing notices marked stale while ordinary run status can still update, and vice versa. Store landing notices by request/attempt, separately from the existing ordinary action notice. Mount/foreground reads restore the bounded retained history; successful refresh, other actions, folding and rerendering do not clear those outcomes. A newer attempt adds a notice instead of overwriting an earlier refusal. Notices outside the returned window stay available on disk; current-session submitted attempts remain pinned in client state. Render each once in its row when visible, otherwise above the list naming the change, preserving Finished behavior.

Both rendered-test harnesses must migrate in the same client integration task: `plugins/nightshift/tests/factory-style-harness.ts:99` and `plugins/nightshift/tests/factory-view.test.ts:97` currently route every RPC except runs to act. Give runs, act, landing status and landing submission distinct descriptors, explicit routes, configurable responses and separate counters; unknown descriptors fail the fixture. Preserve all existing assertions, especially `factory-waiting-view.test.ts:87`'s empty actions after mount and its unchanged run-read count. Added landing reads never increment action or run-read counters.

## Risks / Trade-offs

- Twelve tasks reflect distinct durable-state, process-control and UI boundaries. Roughly 300 changed lines including tests is a planning target, not permission to omit assertions; split a session further when the implementation proves larger.
- A separate plugin-owned script avoids adding an executable dependency to daemon/supervisor modules. Shared adapters must remain control-only; moving launcher imports into them would break the unchanged dependency assertion. The trusted checkout must contain the worker script and matching gateway version; a missing or mismatched installation refuses with retained diagnostics. Host configuration must agree for plugin launch and later jobs control.
- The runner adapter depends on existing land argv. Unknown pre-finish mutations refuse; integration tests must catch drift. Landing still owns the accepted final-base race and possible already-committed remote effects. Stop is not rollback; escaped process groups remain outside termination guarantees.
- Complete evidence grows on disk. Bounded summaries protect status output and memory; metadata enumeration may still cost time on very large stores. This feature adds no evidence deletion policy.
- Permanent landing history remains pending in default jobs inventory because observing a row is not delivery. Documentation must make that exception clear.
- Terminal results are durable, but physical power-loss recovery and real host process ownership cannot be proven by fixture tests alone.

Human checklist for the implementation PR, not agent tasks: after deploy, Matt checks desktop and native phone layout, wrapping and touch targets, confirmation/cancel and stale-dialog behavior, accessible labels, foreground refresh, visible progress, refusal persistence and folded/absent-row placement. Check a real explicitly approved PR's first landing and retained job evidence, and read the updated operator guidance. Native phone/Paseo navigation and real GitHub protections are not established by Node/Python tests; do not report these checks completed before Matt performs them.
