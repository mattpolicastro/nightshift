## Context

`loop.Ctx.repo` is the harness's bare `repo.git`; `Ctx.ref` names the run branch. `loop.finals` performs final coverage/acceptance and pauses ready. `cli._publish`, under the existing run lock, checks `_remote`, pushes, reconciles/adopts a PR, and pauses for human checks. Neither path refreshes `pr_base`. The run repository's own origin points to the source clone, so fetching that origin would not necessarily fetch the hosted base.

`loop.section_evidence` passes `RunState.section_base[section]` and the current head to `evidence.gather`, which uses a two-tree diff. If a base merge occurs between those commits, its upstream additions become mutation candidates. Changing only publication would leave this defect in resumed/revision sections.

`nightshift/specloop_intake.py::publish_pending` saves human checks before calling publish in a receipt keyed by `(change, head, pr)`. It discards a receipt when status reports another head, and skips `human_checks` runs without a matching receipt. Publishing H as merged M in one invocation would therefore lose recovery after a lost publish response or interrupted comment delivery. The publication path must preserve this existing contract without editing intake.

Read sources include README, CLAUDE.md, engine documentation, known limitations, the affected code, and the current interface, run-actions, preparation, revision, intake and parallel-evidence requirements. No AGENTS.md exists in this checkout or its ancestors. #14 is archived here; preserve its strict authored scenario validation and runtime filtering.

## Goals / Non-Goals

Publish a head that incorporates the latest fetched PR base and has passed trusted verification after integration. Keep fetches bounded to one per readiness/publish check; preserve branch history and receipts. Make conflict, failure and interrupted-check behavior testable using temporary local repositories.

Do not change the daemon, supervisor, verification implementation/sandbox, reviewer contracts, manifest, mutation execution, or `finish`. Do not attempt to fix the earlier spec-stage collisions in this change. Do not bypass target validation or change PR adoption/reconciliation. Do not add an automatic rebase, force push, conflict-resolution agent or hosted service dependency to tests.

## Decisions

### One shared gate, two entry points

Add `loop.prepare_publish(ctx, *, remote=None) -> bool`. A true result means the run's current head is eligible to continue; false means the helper durably paused the run with diagnostics. Call it at the start of `finals`, before coverage/acceptance, and reload `head` afterwards so final checks evaluate the merged tree. If final checks append tasks, the next trip through finals checks again. No readiness notification precedes this gate.

In `cli._publish`, preserve the readiness precondition and call `_remote(ctx)` first. Capture `entry_head = ctx.head()` and the existing readiness detail, then pass the validated URL to the shared helper before `_push`, PR lookup or PR creation. A false result returns a nonzero refusal using the existing version-1 outcome with the pause detail in `reasons`; `act publish` retains the mapped refusal detail. A true result must also pass the head-stability boundary below before publication. Re-read the head for the published event. A push/PR transport failure retains today's retryable `ready_to_publish` state and PR reconciliation behavior.

The loop resolves the source clone's origin with `git -C <m.repo> remote get-url origin`; it does not impose a GitHub publishing requirement on a build-only manifest. Fetch exactly `refs/heads/<m.pr_base>` from that URL into a dedicated `refs/specloop/publish-base` in the run repo, with `--no-tags` and an explicit forced destination refspec. Resolve relative local origins relative to the source clone, not the run directory. Do not mutate source refs, configuration or working trees. Use argv, a 300-second fetch timeout, noninteractive prompting, and the user's credential-helper configuration as `_push` does. Keep merge operations on `seal.git`'s safe flags and `seal.IDENTITY`; credential configuration is needed only at the transport boundary. Provide a small `_fetch_publish_base(ctx, remote)` boundary for focused transport stubs.

A failed fetch or missing base pauses as unscheduled `base_fetch` with the requested ref and diagnostic, leaves the branch unchanged, and does not use a previously fetched ref. This adds no supervisor policy. Existing generic pause/status rendering suffices; include explicit `specloop resume <change>` recovery instructions in detail.

### Separate publication-time head advancement from external publication

After `prepare_publish` succeeds, compare the actual head with `entry_head`. If it changed, end this invocation before push, PR lookup/creation, the `published` event, or the `human_checks` pause. Keep the merged, verified head durably paused at `ready_to_publish`. Preserve every human-check item and the trailing `Next: specloop publish` instruction in the readiness detail; update only its leading head summary to the actual head. Use `Run.pause` to save that refreshed detail without an extra readiness notification. A pending integration recovered during this invocation is subject to the same comparison.

For `publish --json`, return exit 1 and exactly `{"version": 1, "error": "<retry explanation>"}` with no `outcome` or `reasons`. Set `args.document` directly, as `_locked_command` does for a retryable busy lock. The explanation names the old/new heads, says integration and verification passed but nothing was published, and instructs `specloop publish <change>` again. For plain publish, print the same explanation and return 1 without a traceback. For the existing `act` wrapper (its internal arguments have a document but no JSON flag), provide the explanation through `reasons` and return 1, preserving its version-1 `refused`/`detail` contract. The daemon calls direct `publish --json`, so it receives the retryable error, never a domain refusal that it would cache and label `needs-human`.

On the next eligible daemon poll, status reports M and `ready_to_publish`. Existing intake discards the H-keyed receipt, saves a fresh M-keyed receipt containing the retained checks, then calls publish again. That invocation fetches once; if the base is still incorporated and M is already verified, it neither merges nor verifies again and can push M and enter `human_checks`. If another base advance produces N, it defers again at N. Do not internally retry publish within the same CLI invocation: the status/receipt refresh between invocations is necessary. Apply this boundary to all publish calls, whether or not an adopted PR exists, so no daemon ownership detection or new protocol is needed.

Interruption safety follows from keeping `ready_to_publish` throughout local integration: a crash after H becomes M but before the retry response leaves a ready run whose M-keyed receipt can be recreated. If the successful retry's response is lost after entering `human_checks`, the receipt already matches M; existing recovery supplies the published result. If comment delivery fails before or after GitHub accepts it, existing round markers retry/reconcile the same M receipt exactly once. A later revision head still gets its own receipt and checks. Status must report the actual Git head; do not alias it to H, rewrite daemon receipts from the CLI, relax head matching, or remove the comment requirement. `issue-intake` Publication needs no MODIFIED delta because both its promised effects and recovery remain intact.

### Preserve history and make conflicts transactional

Let H be the current run head and B the successfully fetched commit. If B is an ancestor of H and there is no unresolved verification obligation, there is no integration work: perform no merge and no extra verify. This ancestry check also supports admitted runs without new state fields; an admission SHA need not be invented from a stale local branch. Normal unchanged-base operation costs one network fetch, plus inexpensive local ancestry checks.

Otherwise compute a merge in a disposable harness checkout using `--no-ff --no-commit`, with hooks/signing disabled and harness identity. Do not merge in the source clone. On conflicts, collect sorted unmerged paths using NUL-delimited Git output, retain a diagnostic, discard the disposable checkout, and pause as `base_conflict`. The run ref and tree remain exactly H; no partially merged index is installed in the bare repository. Operational merge errors are diagnostics, not a successful merge or a fabricated file conflict.

On a clean merge, create a commit M whose first parent is H and second parent is B, even when H could fast-forward to B. Import M into the bare repo, then advance `Ctx.ref` with compare-and-swap `update-ref <ref> M H`. Never reset, rebase or force-push the run branch. A ref mismatch prevents publication and reports an unscheduled infrastructure pause. Upstream changes are trusted base content, not agent-authored files to run through the seal path allowlist.

### Durable verification obligation

Add an optional `base_sync` dictionary to `RunState`, defaulting to empty and loaded with `raw.get`, preserving unknown-field compatibility. Its documented keys are `base`, `previous_head`, `merged_head`, `verified_head`, `receipts`, and `retry_verify`. Record the B/H/M integration intent with empty `verified_head` **before** moving the branch. Keep B recorded for evidence attribution after the check succeeds; do not overwrite it merely because a later fetch conflicts. Set `retry_verify` on conflict as well: a human may incorporate the fetched base during repair, and ancestry on resume must not bypass checking that repair. On recovery with the fetched base already incorporated, record that base and verify the repaired head before clearing this flag. Retain each attempt's diagnostics and receipts in a fresh directory under `final/base-sync/`, never overwriting a failed attempt.

Recovery reconciles a saved clean-merge intent against actual ancestry: at H, complete/retry the saved update under the lock; at M or a descendant, retain the verification obligation; an unrelated ref is an infrastructure error. A conflict-only `retry_verify` record has no M to install. A crash after ref advancement or after verification but before saving success therefore cannot treat B's ancestry as proof of verification. Re-fetch first on the next readiness/publish check; if origin moved again, integrate its latest B before verifying. Preserve the prior obligation until the resulting head passes.

Run `verify.run_steps(ctx.repo, head, m.verify, m, out)` and evaluate with `verify.ok(receipts, m.prepare + m.verify)`. This automatically preserves preparation ordering, expected exits, timeouts, network separation and source immutability. Clean transient source/build trees with `verify.cleanup`, retaining logs and receipts. On success save the exact `verified_head` and receipt directory. A later changed head with recorded integration requires a fresh check before publication; a repeated check of the same successful head does not.

On failing prepare or verify receipts, retain M on the run branch, pause as `base_drift` with B, head, failure summary and receipt paths, and perform no external publication. Do not turn this into `_final_fix` or silently append acceptance tasks. Unexpected verification infrastructure errors also block publication, preserve the obligation and available logs, and use unscheduled `infra` with an explicit recovery detail.

Human recovery uses a checkout of the actual run head (including M after drift), commits a descendant repair on the source branch, then uses existing `specloop resume` to import it through `_sync`. Resume alone is not proof of a fix: the persistent obligation forces verification again, including when B is unchanged. Conflict recovery likewise starts from the retained run head. To request agent work without changing `specloop/revise.py`'s pause policy, an operator may explicitly `resume --no-run` and then queue `specloop revise`; existing `agent:revise` applies once the run is running. Direct revision while paused as `base_drift` remains refused. No daemon or revision-rule changes are required or promised.

### Keep section evidence attributable to the section

Add `loop._evidence_base(ctx, section, head)` and use its result as the existing `evidence.gather` base argument. Preserve an absent section base as absent, preserving the existing skip behavior. Without an integrated B, keep the existing section baseline S unchanged. If B is already an ancestor of S, likewise use S.

When a recorded integrated B is an ancestor of the evaluated head but not S, compute a synthetic comparison commit E by merging B into S in a disposable checkout without advancing any run ref. Diff E against head through the existing gather interface. E contains the earlier sections plus upstream content, so this removes the merge's base-only first-parent changes while retaining only changes since this section started. It is the section-scoped equivalent of comparing the run against `git diff B...head`; using that full-run diff alone would incorrectly include earlier sections. Persist the B/S/E/head identifiers with gate diagnostics, and retain the integrated-base record across revision rounds and reloads. A pending merge not yet present in head must not affect its evidence baseline.

If this comparison merge conflicts, pause `gate_evidence` with the paths and baseline identifiers before generating mutants; do not fall back to a contaminated diff, silently skip mutation, mark evidence passed or append strengthening tasks. Existing behavior is unchanged when no base integration crosses the section. Keep known-scenario filtering, mutation-path filtering, sample counts/seeds, classifications, score/timeout rules and reviewer rules untouched. Do not edit `specloop/evidence.py` or `specloop/manifest.py`.

Each numbered task is scoped to one session and approximately 300 changed lines or fewer, including its tests; reuse the new local fixtures and helpers. Use real local Git histories and a bare origin carrying the configured `pr_base`; leave the source clone stale to prove freshness comes from its origin. Stub GitHub calls and capture push ordering. Use controlled verify receipts for portable control-flow tests, plus an existing-style real verifier integration test on the supported macOS test host. Test mutation candidates through the real gather/generation boundary, stubbing execution only; assert run-owned candidates remain, not merely that upstream candidates disappear. Tag tests with every scenario they cover.

Required test names are `test_moved_base_is_merged_and_verified_before_publish`, `test_base_conflict_pauses_without_publishing`, `test_drift_that_breaks_verify_pauses_with_receipts`, `test_unmoved_base_publishes_without_merge`, and `test_base_merge_lines_are_not_mutated`. ## Risks / Trade-offs

- The remote base may move after the fetch and before push/hosted CI. This checks one current snapshot per attempt; it cannot atomically lock the hosted base and deliberately does not spin until the remote stops moving.
- A merge during publish adds one CLI retry or daemon poll before the push. A continuously moving base can defer publication repeatedly. The existing daemon reports the retryable error through its normal failure/health accounting until success; it does not label the PR or require a human acknowledgement. This bounded retry cost preserves comment recovery without changing intake. Manual callers receive an explicit retry instruction, and a stable next attempt only fetches.
- Persisting integration intent before ref movement makes interrupted work recoverable but adds state transitions. Tests must cover both sides of the ref update and success save.
- A synthetic section baseline may conflict even if the actual run merged cleanly because later work resolved the overlap. Pausing with diagnostics is preferable to attributing upstream code to the section; do not relax evidence rules automatically.
- Fetch authentication may fail on an offline host. No stale-base fallback is allowed. The next explicit resume retries with retained evidence.
- New pause details are visible through existing status; the daemon/UI's specialized action lists and attention categorization are not extended here. Operators recover through the explicit CLI instructions.
- Human checklist for the implementation PR: on the next few real runs, record fetch and added verification durations, total readiness-to-publication latency, repository size and whether the base moved. Judge whether the extra verify is acceptably fast on large repositories. CI can prove ordering and the unchanged-base fast path, but cannot establish representative live publish latency. This observation is not an implementing-agent task.
